# RTDE Monitor requirements

Internal specification for the `rtde-monitor` URCap (`funh` / `rtde-monitor`). When a requirement changes, update this document in the same change and add a changelog row. If the implementation and this document disagree, make them match before the change is finished.

## REQ-1 Register operator screen

Application > Operator Screen lists one contribution, `funh-rtde-monitor-robot-monitor`, titled Robot Monitor. Selecting it opens the configuration presenter `funh-rtde-monitor-robot-monitor-config`. That presenter shows a segment selector in the center of the page. Its choices come from `MONITOR_PAGES` in `constant.ts`. The choices are Register and Robot Status. The label uses the system body font and primary text color. The selected segment uses the system active background, and that highlight slides to the newly selected segment. Register is selected when the operator screen is created, and the choice is stored in the operator screen parameters. The Operator Screen then shows that page. Register shows the general-purpose RTDE registers from the [RTDE Guide](https://docs.universal-robots.com/tutorials/communication-protocol-tutorials/rtde-guide.html). Values are subscribed as RTDE outputs, including registers that an external client writes as inputs.

| Section | Fields |
| --- | --- |
| `input_bit_registers` | `input_bit_registers0_to_31`, `input_bit_registers32_to_63`, shown as bits 0–63 |
| `input_bit_register_X` | `input_bit_register_64` … `input_bit_register_127` |
| `input_int_register_X` | `input_int_register_0` … `input_int_register_47` |
| `input_double_register_X` | `input_double_register_0` … `input_double_register_47` |
| `output_bit_registers` | `output_bit_registers0_to_31`, `output_bit_registers32_to_63`, shown as bits 0–63 |
| `output_bit_register_X` | `output_bit_register_64` … `output_bit_register_127` |
| `output_int_register_X` | `output_int_register_0` … `output_int_register_47` |
| `output_double_register_X` | `output_double_register_0` … `output_double_register_47` |

`output_int_register_X` is included because it is a register. It does not appear on the signals screen. A bit cell is on when the value is 1. Input registers on this screen stay read-only. Output registers can be written as described in REQ-5.

## REQ-2 Signal operator screen

Robot Status shows every RTDE controller output that is not a general-purpose register. Field names stay in the protocol spelling so they can be matched to the RTDE Guide. A field whose name ends in `_bits`, including `safety_status_bits`, is shown as a hexadecimal word. Clicking that row opens a square grid of its bits under the row, and clicking the row again hides the grid. The click works on any cube face and does not rotate the cube. Those cells are one quarter of the side length of a bit-register cell. The cell text is the bit index, starting at 0, and a lit cell is green. UINT32 words show bits 0–31. UINT64 words, including the digital input and output words, show bits 0–63. Fields whose names end in `_types` stay hexadecimal and do not open a grid. Sections are Joints, TCP, I/O, Safety and program, Tool, Payload and energy, and Controller. The filter matches the visible label and the protocol name.

Input-only RTDE fields that the controller does not publish as outputs, such as `speed_slider_mask` and `external_force_torque`, are out of scope.

`time_scale_source`, `safety_status`, `safety_mode`, `robot_mode`, `joint_mode`, `tool_mode`, and `runtime_state` use the constant tables in the RTDE Guide. `safety_mode` uses the Safety Status table. `tool_mode` uses the Tool Modes table from the client-interface manual, because the RTDE Guide names that table without repeating it. The number is underlined. Clicking it shows the guide's meaning in orange beside the signal name, and clicking that same number again hides it. A named constant with a description shows both, as `RUNNING: Brakes are fully released…`. A table that has only a description, such as Time Scale Source, shows that description. `joint_mode` shows the clicked joint as `[0]` through `[5]` plus that joint's meaning. A value that is not in the table shows the translated word Reserved. These labels stay in the guide's English. The choice is not saved.

## REQ-3 Backend subscription

The `rtde-monitor-backend` container connects to the controller RTDE interface at `urcontrol-rtde:30004`. The manifest grants the `urcontrol-rtde` service and the `urcontrol-secondary` service used by REQ-5. It exposes WebSocket ingress `websocket-api` on container port 52762.

- `/registers` streams REQ-1.
- `/signals` streams REQ-2.

The default sample rate is 20 Hz. `RTDE_HOST`, `RTDE_PORT`, and `RTDE_FREQUENCY` override the connection that starts with the process. Clicking the Hz label on a screen opens a wheel of integer rates from 5 Hz through 100 Hz. The new rate is applied only after Confirm, and only for the selected page: its RTDE subscription restarts at the chosen rate, and snapshots are pushed to that page at the same rate. Cancel leaves the current rate unchanged. The choice lasts until that page's last client disconnects, including when the configuration selects the other page. The next subscription starts from the default again.

`rtde-monitor-frontend/src/app/constant.ts` holds the product parameters used by the operator screens, including the frequency limits, the default, and the other timing and entry limits. Frontend code imports that file. The backend checks the same frequency limits in `rtde-monitor-backend/src/constants.py`.

A subscription starts when a page is selected and stops when that page's last client disconnects. If the controller rejects a field or a recipe is too large, the backend splits or drops that field, reports it as unavailable, and continues streaming the fields that were accepted. The status line shows how many fields were dropped. That sentence is a link. Choosing it opens a dialog that lists the protocol names and tells the operator to consult `https://docs.universal-robots.com/tutorials/communication-protocol-tutorials/rtde-guide.html` for more detail. The address is `RTDE_GUIDE_URL` in `constant.ts`. Protocol names stay untranslated. The status line does not show controller exception text or the waiting-for-RTDE sentence. It shows Live or Waiting, the page title, the Hz control, and the unavailable-field count only when at least one field was dropped. A field is unavailable only when the controller returns `NOT_FOUND` for that name, or rejects that name with an unknown data type. A closed socket is retried and is not counted. A failed register write can still show its own message on that line.

## REQ-4 Languages

UI chrome and section titles use ngx-translate. Files live in `rtde-monitor-frontend/src/assets/i18n/`. The file name is the PolyScope X language code:

| Language | File |
| --- | --- |
| English | `en.json` |
| Simplified Chinese | `zh-CN.json` |
| Traditional Chinese | `zh-TW.json` |
| Japanese | `ja.json` |
| Korean | `ko.json` |
| French | `fr.json` |
| German | `de.json` |
| Spanish | `es.json` |

`en` is the fallback language. Operator screen titles are the `operator-screen.<componentTagName>.title` entries, because PolyScope reads those keys. Protocol field names inside value cells stay untranslated. Each language file keeps the same keys. Keypad labels and write failures raised by this URCap are translated. Controller and script-interface errors are shown as returned.

## REQ-5 Output register writes

The Register page can change output registers. Input registers and the Robot Status page cannot.

| Control | Action |
| --- | --- |
| Output bit 0–127 | A click toggles the bit and sends `write_output_boolean_register(address, True\|False)` |
| Output integer 0–47 | A click opens the keypad. Confirm sends `write_output_integer_register`. The decimal key is disabled. The value must fit in a signed 32-bit integer |
| Output double 0–47 | The same keypad with the decimal key enabled. Confirm sends `write_output_float_register` |

The keypad is a three-column grid: digits 1–9, then sign, zero, and a decimal key, with delete beside the entry and cancel/confirm below. It does not open the system keyboard. The first digit replaces the current value. Confirm stays disabled until the entry is a complete number.

Writes go out as one secondary program on `urcontrol-secondary:30002`. `SCRIPT_HOST`, `SCRIPT_PORT`, and `SCRIPT_TIMEOUT` override that connection. The WebSocket command is `{ "op": "write", "id", "kind": "bit" \| "int" \| "double", "address", "value" }`. The reply is `{ "type": "write-result", "id", "ok", "error" }`. Only numbers produced by the keypad are inserted into the script. A running robot program can overwrite the same output register the next time it writes it. A successful reply means the secondary program was sent.

## REQ-6 Layout and zoom

Both pages use the same board. Switching the configuration keeps each page's own card order and scroll. The first row keeps the connection status on the left and the filter on the right. Focusing the filter opens the pendant's default alphanumeric keyboard, and a clear button inside the field removes the current text. Where the status line previously showed the RTDE host, the register screen shows Monitor - Register and the signals screen shows Monitor - Robot Status. The Live or Waiting word fades in and out at 0.3 Hz. Each RTDE section is a card. A card title uses the same warm header bar as a Variables section. Integer, double, and field signals are one full-width row, and those rows alternate white and light gray. Bit registers stay a grid of small cells. A lit cell is green. Signal names use the PolyScope body-medium size, the same size as a variable name, and wrap after an underscore instead of between letters. Values are bold. DOUBLE values, and each component of a VECTOR3D or VECTOR6D, are shown with 4 significant digits. That count is `DISPLAY_SIGNIFICANT_DIGITS` in `constant.ts`. A VECTOR6D component that is zero, or that rounds to zero at those 4 decimal places, is shown as `0.0000`. Vector components stay in a fixed two-column grid, and scalar values stay on one line, so a new sample does not change the row height. Integers, bit fields, and VECTOR6INT32 values stay exact. Columns A1 and A2 are 300px wide on both pendant sizes. Each holds one card, stretched to the full height of the board with the same 12px gap used elsewhere on the page. The remaining width is one cube. Its six faces are F, R, B, L, T, and D, and each face holds one card. The cube is the largest square that fits in that remaining area while it turns. An empty position shows its label. A card covers that label, and the card title does not repeat it. Empty positions stay visible so a card can be dragged into them. There are eight positions in total. A card body still scrolls internally when its own values do not fit. Every face shows its values. The face turned toward the screen accepts that scroll, bit clicks, and register writes. While the cube is rotating, the values stay visible and do not update. One second after the cube stops, samples resume. Dragging a side face, an empty face, or the space around the cube rotates it. A click on a side face, with almost no movement, turns that face to the front. The rotation animates, and it is instant when the user prefers reduced motion.

Holding a card header lifts a copy of that card and the copy follows the pointer. Dropping it on another card swaps the two positions. Dropping it on an empty position moves the card there and leaves the previous position empty. A1 and A2 are the full-height positions. The order, the horizontal scroll position, each card's vertical scroll, and the cube angles for each screen are written to `/data/layout.json` in the backend container. An older file that stores only a list of ids, or only order and horizontal scroll, is still read; the next save stores `{ "order": [...], "scroll": n, "cards": { "joints": n }, "cube": { "x": n, "y": n } }`. `cards` maps a card id to that card body's scroll position. `cube.x` and `cube.y` are the rotation in degrees that is restored when the screen is opened again. `order` lines up with A1, A2, then F, R, B, L, T, and D. An older order that used A3, B3, and so on through B8 keeps its first eight entries in those new positions, and a card that sat further right moves into the first vacant position. An empty string keeps that position vacant. The manifest mounts `persistent:/data`, so the file remains after a robot restart and after a URCap update. Reopening the screen restores the horizontal scroll, each card's own vertical scroll, and the cube angle, instead of returning to the start. The bit grid under a `_bits` value stays hidden until that value is clicked. The reset icon at the right of the filter clears that screen's order, horizontal scroll, card scrolls, and cube angle, and returns the cards to the default sequence with the front face forward. The icon is disabled while the cards are already in that sequence, the row is at the start, every card is at the top, and the cube is at 0 degrees on both axes. Filtering turns card dragging off so a partial list cannot overwrite the saved order. The cube can still be rotated while a filter is active. The front card body keeps normal touch scrolling. Only the header captures the card drag.

Sizes in the stylesheets are written in `px` and converted to `rem` at build time with `postcss-pxtorem` (`rootValue` 16), including the precompiled UI Design Library styles. `@media` breakpoints stay in `px`. `1px` borders stay in `px`. The URCap does not set the root font size, `--font-base-size`, CSS `zoom`, or `transform: scale()`. PolyScope X owns the zoom level. At 100% the layout matches the authored pixel sizes. On a TP7 at 135% the same `rem` sizes grow with the surrounding UI.

`.gitignore` excludes dependencies, build output, IDE files, and Python caches so the project can be published without `node_modules`, `dist`, or `target`. Source, this specification, and the vendored RTDE Python client under `rtde-monitor-backend/src/rtde/` stay in the repository.
